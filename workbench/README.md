# Tests

Everything here runs on the machine you build on: no phone, no Darwin files, no kernel toolchain.

```sh
make check          # the lint, the board files, the generated reference, and workbench/run.sh
workbench/run.sh        # the tests alone
```

They need a C compiler, Python 3.12 or newer and git. On the host the driver tests run under the
address and undefined-behaviour sanitizers where the compiler has them (a read or write past a buffer,
or an unaligned load, fails the scenario). With `gcc-aarch64-linux-gnu` and `qemu-user` they are also
built for arm64 and run under `qemu-aarch64`; with `clang` and `lld` the loader is built. What is not
installed is left out, and said.

## How a driver runs without a kernel

`fakekernel/` has just enough of XNU's interfaces for a driver's own source file to be compiled as a
host program: threads are pthreads, the clock is the host's, sysctls go into a table the test reads
and writes, boot arguments are a string the test sets, the kernel has as many cores as the test says.
A driver reaches hardware through one seam: its `rd()` and `wr()` are `board/mmio.h`'s, and built
with `HAKIOS_MMIO_TEST` they are the test's `hakios_test_rd()` and `hakios_test_wr()`, behind which
the test puts a model of the registers. A driver's `/dev` node is read and written by its name
(`fake_dev_read()`, `fake_dev_write()`). The file that is tested is the file the kernel compiles.

The models that several tests use are headers:

| Header | What it models |
| --- | --- |
| `spmi_model.h` | The PMIC arbiter, of version 5, (with `spmi_version_7()`) of version 7 with its two buses, or (with `channel_map`) of version 8, with the peripherals a test puts behind it. It can refuse a write, fail or drop a transfer, or never answer, and counts reads past the channels it says it has. A test can be called before each read (`looked_at`), to give a register a value for exactly one. |
| `rsc_model.h` | The first command slot set of an RPMh sequencer. It records what is triggered, can be deaf or busy, and notices commands written while the set is triggered. |
| `tlmm_model.h` | The SoC's pins. It counts reads and writes, notices a pin made an output before its level was set, and accesses outside a pin's two registers. A test can put a device on the pins (`after_write`). |
| `i2c_device_model.h` | A device on two of the model's pins that speaks I2C: it takes its address and bytes, gives bytes back, can hold the clock or be stuck in the middle of a byte, and counts a line driven high. A second device can sit at another address; registers can be two bytes wide. |
| `cmd_db_image.h` | A command database built in the test's memory, with a canary behind it. |

Each takes its addresses from the board the driver under test reads, so a wrong address in a driver
is an access to nothing, which the model counts.

A scenario is a process: a driver looks its board up once and starts its threads once, as in the
kernel. Run without an argument a test lists its scenarios; `workbench/run.sh` runs each.

The repository describes no phone, so the tests have their own in `workbench/devices`:

| Board | What it stands for |
| --- | --- |

| `phone-video` | A phone with a video-mode panel on an SM7325, every part driver listed, known to the loader by its framebuffer. |

| `phone-buses` | A phone on a made-up chip whose PMIC arbiter is of version 7: its keys, clock and flashlight on PMICs of the arbiter's second bus, this system the arbiter's second. ## Adding a test

- **For a driver:** keep its arithmetic in a header of its own and test that directly; put hardware
  behind one seam and model it. `backlight_driver_test.c` is the example.
- **For a tool:** a small repository or directory of its own for each test, never the checkout
  (`boards_test.py`: `Sandbox`).
- **For a part of the loader:** a part that is plain C is included by a host program as it is, with
  a made-up firmware behind the calls it makes (`loader_window_test.c`: a memory map; `loader_dsu_test.c`:
  two partitions). A part that cannot be included alone can be cut where its plain C ends; the built
  `loader.efi` has to stay the same byte for byte (`arch/arm64/boot/README.md`).
- A test says what it is for in its first lines, and a check says what was expected when it fails.
- **One scenario a process.** Drivers keep their state in statics; a test's `main` lists its
  scenarios when called without one, and `run.sh` runs each in a process of its own, on the host and
  under qemu-aarch64.
- **Let the driver's threads finish.** A scenario that returns while a thread of the driver still writes
  to the log or to stdout ends its process under that thread: now and then (more often under
  qemu-aarch64) the C library aborts on the way out. Wait for the driver's last word before returning.
- **Wait for everything you then check.** A driver's thread writes its values one after another. A
  test that waits for the first and then compares the second passes a thousand times and fails once
  on a busy machine: `WAIT_FOR(a && b, ms)` before `CHECK(a && b, ...)`, not `WAIT_FOR(a, ms)`. `EVENTUALLY(cond, ms,
  ...)` (`fakekernel/fakekernel.h`) is the two with one condition, so that they cannot differ.
- **Break the code on purpose.** Change the driver one line at a time and see that a scenario fails
  each time: `workbench/mutate.sh TEST SOURCE OLD NEW` does it in a copy and says which scenarios caught
  the change, or that none did. A check that no such change can fail checks nothing; a change no
  scenario notices is a scenario to write, or a line that does nothing.

  ```sh
  workbench/mutate.sh ddr_driver_test board/ddr.c 'level == 0 ||' ''
  # caught by: not_listed_not_asked
  ```

  The same text as OLD and NEW changes nothing: the test as it is, with what each scenario that fails
  says -- the first thing to run on a test being written, one test and not all of `run.sh`.

  `workbench/mutants.py TEST SOURCE` makes the simple changes itself -- each comparison turned the other
  way or made inclusive, each `&&` made `||` -- runs every one, and prints those no scenario noticed.
  Some of those change nothing (a `>` that may as well be `>=` when two equal values give the same
  result); the rest are scenarios to write. A change that leaves a scenario waiting forever is caught when
  its time runs out, two minutes by default: `MUTATE_SECONDS=20 workbench/mutants.py ...` makes a run over a
  driver whose scenarios wait take minutes and not hours.
- Add it to `workbench/run.sh` (`make lint` says so of a test that no script of `workbench/` runs).
